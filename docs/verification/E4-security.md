# E4 security checklist (SEC-01 to SEC-08)

What E4 changes against PRD §8.2, with the evidence that each item still holds; items E4 does not touch keep the
evidence of `E1-security.md` to `E3-security.md`. The suites are `pnpm check`, `pnpm test:integration`,
`pnpm test:daemon`, `pnpm test:e2e`, `pnpm test:nfr`, `pnpm test:soak` and `pnpm verify:artifact`, with the macOS
test host up (P-57) where they include it.

| Item     | What E4 adds                                            | Evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Status |
| -------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| SEC-01.1 | This computer's daemon, the LaunchAgent and macOS hosts | The local connection runs the bootstrap with `/bin/sh -s` and then `trcd bridge` over pipes (P-59); the plist has no `Sockets` or `MachServices`, so launchd opens nothing for it (`launchd.rs`); remote Macs are reached only over SSH. `no-listeners.spec.ts` finds no TCP listener or UDP socket in the app's processes, nor in the local core and holders                                                                                                                                                                                                                                                    | Met    |
| SEC-01.2 | The core's socket on macOS                              | The same code as on Linux: `<root>/run/core.sock` 0600 in a 0700 folder, or the `/tmp/trc-<uid>` fallback when the path is too long; the Rust suite runs natively on macOS (P-15), and under Rosetta for the x86_64 slice (P-63)                                                                                                                                                                                                                                                                                                                                                                                 | Met    |
| SEC-01.3 | The check on macOS                                      | `no-listeners.spec.ts` checks after install, connect and session creation on This computer; Linux hosts keep E1's test                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Met    |
| SEC-02.1 | Peer identity on macOS                                  | `is_same_user` reads the peer's uid with `getpeereid` through tokio's `peer_cred` on macOS; the refusal of another user's peer is tested on Linux (`core_linux.rs`, `holder_process.rs`), which can switch users; on the test Mac, `trcnogui` cannot even list `admin`'s install roots, which are 0700 (`ls` checked by hand on 2026-11-17: Permission denied)                                                                                                                                                                                                                                                   | Met    |
| SEC-02.2 | The bridge on macOS                                     | It checks the install root and run folder are the user's and private before it connects (`verify_private_dir`), as on Linux                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Met    |
| SEC-02.3 | This computer                                           | No token or secret: the local link is the user's own `/bin/sh`, and the daemon's peer check is the only gate. The connection host takes a local target only for This computer's host ID and its own install location, which the main process gives it, so the sandboxed renderer cannot aim the local shell elsewhere (`requests.test.ts`)                                                                                                                                                                                                                                                                       | Met    |
| SEC-03.1 | This computer, and macOS hosts                          | This computer runs no ssh; its bootstrap gets only `HOME`, `USER`, `LOGNAME`, `SHELL` and `PATH`, the variables the LaunchAgent keeps, and sessions start with a cleared environment of their own (`local-transport.ts`, `pty.rs`), so nothing changes the user's SSH settings; macOS hosts use the same ssh arguments as Linux ones                                                                                                                                                                                                                                                                             | Met    |
| SEC-04.2 | The universal macOS daemon                              | `darwin-universal/trcd` ships in the app bundle beside the Linux daemons; `pnpm verify:artifact` requires it and checks its SHA-256 against the manifest on each architecture's build                                                                                                                                                                                                                                                                                                                                                                                                                            | Met    |
| SEC-04.3 | The local install, and macOS hosts                      | This computer installs through the same bootstrap as a host: the binary arrives on standard input and its SHA-256 is checked with `shasum -a 256` before it runs; `bootstrap.integration.test.ts` runs its corrupted-upload test on both Mac users                                                                                                                                                                                                                                                                                                                                                               | Met    |
| SEC-04.4 | The core under launchd                                  | The integrity check is the same code on macOS; a core it refuses, which no retry fixes, exits 0 under launchd, so `KeepAlive` does not restart it every second; a crash, a SIGTERM that leaves the job loaded (`kill`, `launchctl stop`, both in the test below, or Activity Monitor's Quit), or an error the OS may get past (`StartError::may_pass`) restarts it within a second, while a logout or `bootout` unloads the job (`tests/launchd.rs` `registers_the_core_as_a_launch_agent_that_keeps_every_session`, run on this Mac's GUI session) (`Supervisor::refusal_status` and its tests in `command.rs`) | Met    |
| SEC-05.1 | Local sessions' records and scrollback                  | They live under the TRC home's `sessions/`, 0700 and 0600, by the same store code; the app creates the TRC home 0700, and the bootstrap refuses an install root others can change                                                                                                                                                                                                                                                                                                                                                                                                                                | Met    |
| SEC-07.1 | The LaunchAgent                                         | It is registered in the user's own `gui/<uid>` domain with `launchctl bootstrap`, with no administrator step; its plist is written 0600 in `~/Library/LaunchAgents`, the one file outside the install root (P-61), and Remove daemon boots the agent out and deletes it (`local-connection.integration.test.ts`); a Mac host without a GUI login registers nothing                                                                                                                                                                                                                                               | Met    |
| SEC-08.1 | `launchd.log`                                           | The plist sends the core's standard error to `logs/launchd.log`, which gets only the core's exit messages, an error's own text such as a refused install (`main.rs`), or a panic's; no code path writes output, input or environment values there; when the core never comes up, the bridge passes its last 3 lines, each cut to 300 characters, into its error, which the app shows in the failure's details and does not log; the core's JSON log is unchanged                                                                                                                                                 | Met    |
| SEC-08.2 | `launchd.log` and the plist                             | The plist's `Umask` is the bridge's, 077 under the bootstrap, and the bridge creates `launchd.log` 0600 in the 0700 `logs/` folder before launchd opens it, whatever that umask (`create_private_log`; `tests/launchd.rs` `registers_the_core_as_a_launch_agent_that_keeps_every_session` asserts the mode); a starting core empties it once it passes 1 MiB, as nothing rotates it (`trim_log`, which follows no symbolic link)                                                                                                                                                                                 | Met    |
| Tooling  | The macOS test VM                                       | lima's user-mode network forwards only the VM's SSH, to `127.0.0.1:2230`, which every local process may reach but only the test key opens; nothing else is published (D-53, `tools/test-hosts/macos/up.sh`). The image's well-known password opens SSH from loopback until `up.sh` ends its provisioning, then is turned off; the VM is deleted at the end of E4 (P-57)                                                                                                                                                                                                                                          | Met    |
