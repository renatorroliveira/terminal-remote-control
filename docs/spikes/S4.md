Client: the system `/usr/bin/ssh`, OpenSSH 10.5p1 (LibreSSL 3.3.6). Servers: OpenSSH 10.2 in the test hosts. The
corpus, with stderr verbatim and machine paths replaced by `<run>` and `<app>`, is in [`s4/`](s4/).

## Host keys (US-1.2)

The `known-hosts` helper prints `<nonce> HOSTKEY %H %t %K %f` on stderr and returns no keys; it ignores the
`%I=ORDER` call.

| Case                    | stderr (after the HOSTKEY line)                                                         |
| ----------------------- | --------------------------------------------------------------------------------------- |
| Unknown key             | `No ED25519 host key is known for [127.0.0.1]:2221 and you have requested strict checking.` |
| Changed key             | The `REMOTE HOST IDENTIFICATION HAS CHANGED` banner, then `Host key for [127.0.0.1]:2221 has changed and you have requested strict checking.` |

- The helper path may contain spaces when quoted inside the config value.
- `%H` is already in `known_hosts` form (`[127.0.0.1]:2221`, or the alias' `HostName`), so accepting a key appends
  `%H %t %K` (hashed when `ssh -G` reports `hashknownhosts yes`).
- The helper runs for every connection, so its line also appears on success; the app strips HOSTKEY lines from
  anything it shows.

### ProxyJump finding (changes the design)

For `ProxyJump`, ssh runs the jump connection as `ssh -F <config> -W '[%h]:%p' <jump>`. **None of the app's `-o`
options reach it**: no BatchMode, no strict checking, no KnownHostsCommand. The jump connection fell back to an
interactive host-key prompt, which only failed because the app's `askpass` refuses every prompt.

Fix, verified through the jump-host pair:

- The connection host writes a **wrapper config** per connection: a `Host *` block with every security option from
  TECH_STACK §7, then `Include ~/.ssh/config` and `Include /etc/ssh/ssh_config` (ssh reads neither on its own once
  `-F` is given).
- It passes the wrapper with `-F` and keeps the same `-o` options on the command line, so US-1.1.4 holds literally.
- ssh keeps the first value it obtains, so the `Host *` block wins over the user's config, and the jump connection,
  which receives the same `-F`, gets the same protections.
- Results: an unknown jump key is reported through the helper with its own `%H`, then the unknown target key; once
  both are accepted the connection succeeds. `ClearAllForwardings yes` does not break the `-W` stdio forward.
- The P-14 test seam becomes the include target: test builds replace `Include ~/.ssh/config` with
  `TRC_TEST_SSH_CONFIG`, and `TRC_TEST_KNOWN_HOSTS` sets `UserKnownHostsFile` in the wrapper.

## askpass (US-1.1.3, US-1.3.2)

- With BatchMode, a passphrase-protected key without an agent never reaches `askpass`; ssh fails with
  `Permission denied (publickey).` So the app never prompts for a secret.
- Without the wrapper, the jump connection's host-key question reached `askpass` as a prompt
  (`The authenticity of host … can't be established`), which the helper refused. With the wrapper, nothing reaches
  `askpass` except notices.
- **FIDO touch:** no security key was available in this session. The helper prints `<nonce> NOTICE <text>` when
  `SSH_ASKPASS_PROMPT=none` and refuses everything else; OpenSSH's `notify_start()` sends "Confirm user presence for
  key …" that way. The real touch flow moves to the ST-21 manual checklist.

## Failure corpus (US-1.3)

| Case                               | exit | stderr                                                         | How the app tells it apart                    |
| ---------------------------------- | ---- | -------------------------------------------------------------- | --------------------------------------------- |
| No agent running                   | 255  | `tester@127.0.0.1: Permission denied (publickey).`             | `ssh-add -l` exits 2                          |
| Agent has no identities            | 255  | same                                                           | `ssh-add -l` exits 1                          |
| Passphrase key not loaded          | 255  | same                                                           | an `IdentityFile` from `ssh -G` fails `ssh-keygen -y -P '' -f`, and its public key is not in `ssh-add -L` |
| Expired certificate                | 255  | same                                                           | a `CertificateFile` from `ssh -G` whose `ssh-keygen -L` validity has ended |
| Key rejected by the host           | 255  | same                                                           | none of the above                             |
| Key needs a PIN (FIDO)             | —    | not reproducible without a key                                 | `sk-` key type in `ssh-add -L` or `IdentityFile`; message from OpenSSH source |
| DNS failure                        | 255  | `ssh: Could not resolve hostname no-such-host.invalid: …`      | text                                          |
| Host unreachable                   | 255  | `ssh: connect to host 127.0.0.1 port 2299: Connection refused` | text                                          |
| Timeout                            | 255  | `ssh: connect to host 10.255.255.1 port 22: Operation timed out` | text                                        |
| Jump host failure                  | 255  | `ssh: connect to host 127.0.0.1 port 2299: Connection refused` | the named host/port is not the target's, and `ssh -G` shows a `proxyjump` |
| Unknown / changed host key         | 255  | see above                                                      | text plus the HOSTKEY line                    |

- `Permission denied (publickey)` carries no reason at `LogLevel=ERROR`, so the classifier runs the local checks in
  the order of the table and falls back to "key rejected".
- The expired certificate showed a HOSTKEY line first, so the host was reached; DNS, refused and timeout failures
  never print one.
- Exec-only hosts: with `DisableForwarding yes` on every test host except the jump host, `exec` works (US-1.5.3).

## Agent discovery from Finder

macOS launchd sets `SSH_AUTH_SOCK` for the GUI session (`launchctl getenv SSH_AUTH_SOCK` returns
`/var/run/com.apple.launchd.<id>/Listeners`), served by `com.openssh.ssh-agent`, so an app launched from Finder sees
the same agent as Terminal. Agents configured through `IdentityAgent` are read by ssh from the config. No login-shell
environment read is needed (TECH_STACK §4.2 stands).

## Consequences for the plan

- ST-8 builds the wrapper config (D-21) in addition to the command-line options, and the classifier follows the
  table above.
- ST-8's integration tests reuse these cases against the test hosts.
