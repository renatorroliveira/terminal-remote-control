# Spike S13 — The renderer to connection-host path on a sub-millisecond link

| Field    | Value                                                                                    |
| -------- | ---------------------------------------------------------------------------------------- |
| Date     | 2026-11-14                                                                               |
| Story    | ST-35 (E2)                                                                               |
| Retires  | NFR-02's E1 exception (the app added 10.2 to 10.7 ms at p95 on a sub-millisecond link)   |
| Decision | D-47: the app turns off Chromium's `DeferRendererTasksAfterInput`; NFR-02 holds at 10 ms |

## What was built

Throwaway measurements against `trc-ubuntu` (round trip about 1 ms) and `trc-latency` (100 ms), in a test build:

- The connection host stamped, with `performance.timeOrigin + performance.now()`, each input request it received,
  each chunk read from ssh's stdout, and each output post to the renderer, kept in memory and written out once a
  second. The renderer stamped each keydown, and the P-14 write timing gave when each output arrived and when xterm
  parsed it. 100 keystrokes, 45 ms apart, paired each keydown with the first output after it.
- At the connection host alone (the NFR harness's `LiveHost`): ping to pong over the channel, the echo of a
  keystroke through bash, and the echo from the PTY itself (`stty raw echo; sleep`), 100 samples each.

## Results

On `trc-ubuntu`, p50 / p95 in ms:

| Segment                                             | Before  | With D-47 |
| --------------------------------------------------- | ------- | --------- |
| Keydown to the input request at the connection host | 0.4/0.6 | —         |
| Input request to the echo read from ssh             | 3.0/4.6 | —         |
| Echo read from ssh to its post to the renderer      | 0.0/0.0 | —         |
| Post to the renderer receiving it                   | 5.1/9.2 | —         |
| Parsed by xterm after it arrived                    | 0.1/0.2 | 0.1/0.2   |
| Keydown to the echo parsed                          | 8.4/13  | 4.2/5.6   |

- **The spread is the renderer's scheduler, not message delivery.** The same output posted without a keystroke
  before it arrives in 0.14 ms at p50. After a key press, Chromium's `DeferRendererTasksAfterInput` holds every
  task but rendering until the next frame, so the echo waits up to one 10 ms frame on a 100 Hz display, half of one
  on average. Turning it off (`--disable-features=DeferRendererTasksAfterInput`) removes the wait. The app's own
  frames do not change: the echo still reaches the text surface at the next frame.
- At the connection host, ping is 1.06/1.38 ms, the bash echo 3.89/5.85 ms and the PTY's own echo 3.31/5.81 ms:
  the daemon's path through the core, the holder and the PTY costs about 2.3 ms at p50 on these hosts, and bash
  adds little. That leaves room under 10 ms, so it stays as it is.
- With D-47 the UI test measures 6.0 ms at p95 on `trc-ubuntu` against an 11.1 ms budget, and 117.3 ms on
  `trc-latency` against 117.7 ms. On that host ping itself is 109.6 ms at p50 and 115.0 ms at p95: the 100 ms
  test link jitters by about 5 ms, which NFR-02's median round trip leaves inside the app's 10 ms; the app adds
  2 to 3 ms over the link's own p95.

## Decisions

- D-47 in `docs/TECH_STACK.md`: the main process appends the switch before the app is ready
  (`src/main/latency-switches.ts`).
- The UI test's 15 ms local allowance is gone: NFR-02 is checked at the PRD's 10 ms on every link.
