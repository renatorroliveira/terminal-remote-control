# Spike S2 — Accessible Text Surface: selection, caret and input on macOS

| Field    | Value                                                                                                          |
| -------- | -------------------------------------------------------------------------------------------------------------- |
| Date     | 2026-11-12                                                                                                     |
| Story    | ST-1 (E1)                                                                                                      |
| Retires  | R1 (macOS), the A11Y-04 and A11Y-06 mechanism, A11Y-09.3–4                                                     |
| Decision | Keep the ATS design. **Input goes through a `contenteditable` element that cancels every edit, not EditContext** (D-22). |

## What was built

A throwaway Electron 45.3.1 app (`spikes/s2`): sandboxed renderer, `app://` scheme with the TECH_STACK CSP, xterm.js
6.0.0 with the WebGL renderer and the graphemes addon, and an ATS prototype over the canvas:

- a `div` with `role="textbox"`, `aria-multiline="true"`, `aria-label` and a hint, `tabindex="0"`;
- one absolutely positioned row `div` with one text node per terminal row, in the same font and cell metrics, with
  transparent text;
- selection mirrored from xterm into the DOM with `setBaseAndExtent`, and from the DOM into xterm with `term.select`;
- a collapsed DOM caret at the terminal cursor when nothing is selected;
- three input variants: EditContext, `contenteditable` with `beforeinput` cancelled, and a read-only text box.

The Swift probe (`tools/ax-probe`, kept) reads the focused element's AX attributes.

## Attribute mapping (probe, Chromium 156)

| Attribute                                   | Result                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| `AXRole` / `AXRoleDescription`              | `AXTextArea` / "text entry area" in every variant                         |
| `AXTitle`, `AXDescription`                  | the `aria-label` ("spike, localhost")                                     |
| `AXHelp`                                    | **absent** for both `aria-description` and `aria-describedby`             |
| `AXFocused`                                 | true                                                                      |
| `AXValue`, `AXNumberOfCharacters`           | all rows, joined with `\n`                                                |
| `AXSelectedText`, `AXSelectedTextRange`     | the mirrored selection ("quick brown fox", `{54, 15}`)                    |
| `AXSelectedTextMarkerRange` + `AXStringForTextMarkerRange` | the same selection                                         |
| Collapsed caret                             | `AXSelectedTextRange` `{133, 0}` at the terminal cursor                   |
| `AXBoundsForTextMarkerRange` (caret)        | the caret rectangle at the cursor cell, **only with `contenteditable`**   |
| `AXBoundsForRange`, `AXLineForIndex`, `AXRangeForLine`, `AXInsertionPointLineNumber` | unusable: Chromium treats the field as one line and returns empty bounds |

- Chromium reports caret bounds reliably only in its full accessibility mode, which VoiceOver turns on with
  `AXEnhancedUserInterface`. The probe now does the same.
- With **EditContext**, the full mode either reported no focused element or an empty rectangle at the window's
  corner. With VoiceOver and Zoom on, **Zoom bounced to that corner and back on every keystroke**. With
  `contenteditable`, the caret rectangle was correct on every read and moved one cell per typed character, and Zoom
  followed the cursor smoothly.
- Selection mirroring works in both directions in every variant once the rules below are in place.

## Owner's manual checks (VoiceOver, Zoom, Dictation, IME)

Final run with the `contenteditable` variant: all checks pass.

- VoiceOver reads the name and role and the text; keyboard focus behaves; typing echo is not doubled.
- Selections are real OS selections: VO+F6 and Speak Selection read them, and the OS reports the selected text.
- Zoom follows the cursor while typing; the Japanese IME candidate window appears at the cursor and commits once;
  dictation inserts text once.
- Look Up, Services, select-all and responsiveness under a flood were not flagged.

Bugs found and fixed during the checks, and now ATS design rules:

1. **Mouse drag did not select** (double-click and Shift+click did). Writing the DOM selection while the pointer is
   down cancels Chromium's native drag. Rule: while the primary button is down in the ATS, the DOM selection is the
   source of truth and is only mirrored into xterm.
2. **Typing kept the selection.** Rule: input clears the selection, scrolls to the bottom and moves the caret back
   to the cursor in a single selection change (never remove-then-set, which made Zoom jump).
3. **A selection made by AT or the keyboard was overwritten by the caret.** Rule: a non-collapsed DOM selection inside
   the ATS that the app did not set is never replaced by the caret; it is mirrored first.
4. Row text updates use minimal `replaceData` edits, so a caret inside a changing row keeps its position instead of
   collapsing to the row start.

## Consequences for the plan

- D-22: the ATS is a `contenteditable` `div` with `role="textbox"`. Every `beforeinput` is cancelled and its data
  sent to the PTY; IME text is sent on `compositionend`, and the row is restored on the next update. EditContext is
  not used, because it breaks caret bounds for Zoom (A11Y-06.3).
- ST-10 implements the four rules above, and `pnpm test:ax` asserts the mapping table with the probe.
- **Open for ST-10 (A11Y-01.2):** the hint is not exposed as `AXHelp`. ST-10 tests VoiceOver's reading of
  `aria-describedby`, and if VoiceOver does not speak it, folds the hint into the accessible name behind the
  verbosity setting.
- `updateSelectionBounds` and `updateControlBounds` were EditContext APIs; with `contenteditable`, IME and dictation
  placement come from the DOM caret, which the owner confirmed.
