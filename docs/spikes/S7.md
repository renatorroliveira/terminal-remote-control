# Spike S7 — The on-disk scrollback after a crash or power cut

| Field    | Value                                                                                                |
| -------- | ---------------------------------------------------------------------------------------------------- |
| Date     | 2026-11-16                                                                                           |
| Story    | ST-40, folded into ST-42 (E3)                                                                        |
| Retires  | NFR-08's open question: whether an append-only log stays readable when a write is cut short          |
| Decision | One append-only file of checked records per session, each consistent on its own; see TECH_STACK §5.5 |

## What was built

The format and its writer, tested where they live (`crates/trcd/src/holder/scrollback_file.rs`,
`scrollback_writer.rs` and `persistence.rs`) rather than as a throwaway prototype, since the tests are the evidence:

- Every record holds the history rows that left the screen since the record before and, when it changed, the
  primary screen at that moment: `[u32 length][first 4 bytes of the payload's SHA-256][payload]`. So the records up
  to any point give a consistent history and screen, and a restore needs no second file to agree with the first.
- Appends are synced (`fdatasync`) as they are written, on a thread of their own, at most 2 s after the output.
- A rewrite builds `scrollback.log.new`, syncs it, renames it over the old file and syncs the folder.

## Results

- **Cut short at every byte.** Reading a file of three records cut at each of its offsets keeps exactly the records
  before the cut, and says the rest was dropped. A flipped byte inside a record stops reading at that record, and a
  length beyond the largest record (64 MiB) is never trusted.
- **Failed writes.** A write that fails cuts the file back to where it was, so later appends never follow a torn
  record; the holder reports the cause (disk full, quota, read-only, other) and writes a whole new file 10 s later.
- **A slow disk.** The writer holds at most 4 MiB of records; past that, records are dropped and the holder writes a
  whole new file once the queue has drained, so saving never grows a holder's memory beyond that (NFR-09).
- **Lag.** Through the core on macOS, the integration test finds 300 lines of output in the file within NFR-08's
  5 s of printing them; `pnpm test:nfr` measures the lag on Linux (ST-49).
- **Size.** A file is rewritten once the rows appended to it outnumber both the scrollback limit and the rows the
  last rewrite wrote, so it holds about twice the history at most. S12 measured the formatted history at about 62 bytes a row, and 8 ms to format 30,000 rows.
- **Reflow.** Rows already saved keep the width they had; a resize asks for a rewrite, so the file follows the
  reflowed history at the next save.

A host that loses power mid-write loses at most that write and the 2 s before it. The reboot integration tests and
the reboot soak (ST-44, ST-49) restart the test hosts with sessions printing, and read the files back.
