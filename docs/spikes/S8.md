# Spike S8 — launchd, holders and macOS hosts

| Field    | Value                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------- |
| Date     | 2026-11-17                                                                                                |
| Story    | ST-52 (E4)                                                                                                |
| Retires  | R4, R5 and R7 on macOS: what ends a session under launchd, a logout and a reboot, and macOS as a host     |
| Decision | The plain LaunchAgent stands (D-50); logout ends no session (P-62, US-4.4.2 amended); prompts kept (P-66) |

## What was built

Two throwaway probes (P-06), committed once as evidence and then deleted:

- `crates/trcd/tests/s8_spike.rs`, on this Mac: a core run as a temporary LaunchAgent `dev.trc.test-<random>` with
  a scratch install root (P-58), whose plist stays in the scratch folder. It creates a session, then checks the
  shell's process ID through `launchctl kickstart -k`, a `kill -9` of the core that `KeepAlive` answers, and
  `bootout` followed by `bootstrap`.
- `apps/desktop/test/soak/s8-vm.soak.test.ts`, against a tart VM of macOS 26.6.2 (arm64, 4 CPUs, 8 GiB) through the
  connection host, as the app connects: the bundled universal daemon is uploaded, verified and run over SSH. Two
  users: `admin`, whom the image logs in to the GUI at boot, and `trcnogui`, who never has a GUI login. For the GUI
  user, the probe replaces the detached core with a hand-written LaunchAgent, which ST-54 then builds.

## Results

- **launchd keeps every holder.** Holders call `setsid()`, so `kickstart -k`, a killed core, and `bootout` then
  `bootstrap` each leave the shell running, and the next core adopts it (the same process ID before and after). A
  LaunchAgent core also adopts the holders that a detached core started.
- **Without a GUI login** the bridge's detached core runs as on Linux. Sessions outlive the SSH connection (alive
  20 s after it closed, the same shell on reconnect). After a reboot no core runs until the app connects; then each
  session respawns below its saved scrollback with the "Session restored after restart" marker and
  `afterHostRestart`, as the boot ID from `kern.bootsessionuuid` changed.
- **With a GUI login,** after a reboot the image logs `admin` in, the agent's `RunAtLoad` starts the core (one run),
  and it respawns every session before the app connects.
- **Logout ends no session.** Logging the GUI user out (`loginwindow`'s "really log out" event) unloads the
  `gui/<uid>` domain and the agent's core with it, but every holder and its shell keep running. The next connection's
  detached core adopted them: the same shell, and typed input came back. So US-4.4.2's premise ("logging out ends
  user processes on macOS") does not hold, and the owner chose to keep sessions across a logout (P-62).
- **`launchctl print gui/<uid>`** tells over SSH whether the user has a GUI login session: it succeeds for `admin`
  while logged in, and fails for `trcnogui` and for `admin` after the logout (P-61).
- **Privacy prompts.** A command that reads `~/Desktop`, `~/Documents` or `~/Downloads` in a session under the
  LaunchAgent waits for a prompt: TCC attributes the access to the responsible process, the agent's `trcd`, whose
  identifier `trcd-<hash>` comes from its ad-hoc signature, and logs `AUTHREQ_PROMPTING` for
  `kTCCServiceSystemPolicyDesktopFolder`. Under the detached core or SSH, the same command finished at once. The
  prompt could not be answered in a headless VM, so whether a new daemon version is asked again was not observed;
  as the identifier follows the signature, it is assumed. The owner accepted the prompts for 0.x (P-66).
- **The universal binary** is 6,528,192 bytes. Both slices and libghostty-vt target macOS 13.0, which covers PRD
  §7.2's current and previous two releases (26, 15 and 14). Under Rosetta, installed in the VM with
  `softwareupdate --install-rosetta`, `arch -x86_64 trcd --version` runs the x86_64 slice. A stock Mac has no
  `lipo` (it needs the developer tools), so the bootstrap never calls it; `shasum` is there.
- **The test VM's network.** Tart's shared NAT gave the VM no address on this managed Mac: the VM's frames reached
  `vmenet0` but never `bridge100`, and `bootpd` never ran. On lima's user-mode network (`limactl usernet`) through
  `tart run --net-fd`, with a static lease and the VM's SSH forwarded to `127.0.0.1:2230` only, it was reachable
  within seconds of boot (P-67, D-53). The image's password login was used once to add the test key, then turned
  off.
- **`KeepAlive`** restarts a core on any non-zero exit, every 10 s at most. A core refused because another core runs
  (75) or because the install is not private (78) would therefore loop under launchd; the first probe run hit 78
  when it made a `logs/` folder of mode 0755 (ST-54).

## Changes to the plan

- P-62 rewritten: a logout ends no session; only a reboot respawns shells.
- P-66: the privacy prompts stay in 0.x and the user guide explains them; E8's signing makes answers last.
- P-67, D-53: the VM's network; §3.4's `up.sh` follows it.
- D-54: the universal2 build, macOS 13.0 as the deployment target, and the release's daemons built on `macos-15`.
- ST-54 makes a refused core exit without a restart loop under launchd.
