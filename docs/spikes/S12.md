# Spike S12 — Streaming a snapshot in blocks of rows

| Field    | Value                                                                                |
| -------- | ------------------------------------------------------------------------------------ |
| Date     | 2026-11-14                                                                           |
| Story    | ST-23 (E2)                                                                           |
| Retires  | NFR-09's E1 exception (a snapshot held whole, and copied, while it is sent)          |
| Decision | Snapshots stream in blocks of rows from tracked grid references; see the rules below |

## What was built

A test inside `trc-vt` against libghostty-vt 1.0.1. A terminal of 80×24 with a 100,000-line limit was fed 30,000
lines mixing SGR styles, true color, wide and emoji characters, tabs, rows that soft-wrap and a pending style.
The history was formatted 500 rows at a time with the formatter's selection (`GHOSTTY_POINT_TAG_HISTORY`, VT,
no extras, no trimming), then the screen (`GHOSTTY_POINT_TAG_ACTIVE`) with the snapshot extras. The blocks were
fed to a fresh terminal and compared with one fed the whole snapshot.

## Results

- The blocks replay identically, once two rules are kept: a block whose last row does not soft-wrap is followed by
  `CR LF`, which the formatter writes only between rows; and before the screen block come `rows − 1` line feeds and
  `CSI H`, since the screen's extras set the scrolling region, which homes the cursor. Plain text, cursor and a
  second VT snapshot of both terminals then match.
- 29,978 history rows: 1.87 MB in total, the largest 500-row block 31 KB, the screen 1.5 KB. Formatting it all took
  8 ms in a release build.
- Tracked grid references (`ghostty_terminal_grid_ref_track`) follow their row as output arrives and report no value
  once pruning removes it, so a stream can resume at its next row or skip what pruning took.
- **E1 bug found:** while the alternate screen is active, the formatter sees only that screen. E1's snapshot then
  carries neither the primary screen nor its scrollback, so a reattach during vim, less, htop or tmux loses the
  history above once the program exits. The libghostty-vt API has no way to format the inactive screen; its binary
  snapshot (`ghostty_snapshot_encode`) holds both.

## Consequences

- ST-25 streams snapshots in blocks within the attachment's credit, resuming from a tracked reference, and ends with
  the screen and its extras.
- While the alternate screen is active, ST-25 takes the primary screen and its scrollback from a binary-snapshot copy
  decoded into a temporary terminal, streamed the same way, then the alternate screen from the live terminal. That
  copy exists only while such a snapshot streams; ST-36 measures it against NFR-09.
