## SSH

### How Windows OpenSSH starts the helpers

A throwaway probe program (Rust, logging its command line, arguments, environment and console) stood in for both
helpers, from a folder with a space and a non-ASCII letter in its name, run by an ssh that a console-less Node process
started, as Electron's utility process is.

- **`KnownHostsCommand`** runs as a command line: `"<path>" known-hosts %I %H %t %K %f` reaches the program as
  `known-hosts`, then ssh's tokens, with the quoted path intact. The `ORDER` call comes first, as on macOS
  (`known-hosts ORDER 127.0.0.1 NONE NONE NONE`), then `HOSTNAME [127.0.0.1]:2221 ssh-ed25519 <key> SHA256:<hash>`.
- **`SSH_ASKPASS`** runs as a command line too, unlike Unix ssh, which `exec`s the value as one path:
  `"<path>" askpass` reaches the program as `askpass <prompt>`. So `trcd.exe`'s subcommand fits in `SSH_ASKPASS` with
  `SSH_ASKPASS_REQUIRE=force`, and no copy of the binary under another name is needed. The integration suite runs the
  real ssh with it, so a later Windows OpenSSH that quoted the value differently would fail there.
- **Console windows.** Without `windowsHide`, ssh gets a new console, and each helper inherits it: a visible window
  (`IsWindowVisible` 1) flashes on every connection. With `windowsHide` (`CREATE_NO_WINDOW`), the helper has no console
  at all. So the connection host starts ssh, `ssh-add` and `ssh-keygen` hidden, and `trcd.exe` can stay a console
  program for 0.7.0; 0.8.0's core, started at login, is S15's question.
- **A hidden console still reads input.** An ssh started hidden without `BatchMode`, for a passphrase-protected key,
  waits for a passphrase on its invisible console forever, where macOS's ssh fails at once for want of a terminal. The
  app always passes `BatchMode=yes`; the test suites' own ssh calls now do too.

### Configuration and output

- `ssh -G` prints CRLF line ends, and the app's parser read `\r` into every value; it now splits on `\r?\n`, as does
  the stderr classifier, whose `connect to host … (.+)$` could not match a line ending in `\r`.
- `ssh -G` reports `UserKnownHostsFile NUL`, `nul`, `/dev/null` and `none` as written; Windows OpenSSH discards keys
  for each, so D-58's check counts `NUL` in any case (P-91).
- The default user files are `C:\Users\<name>/.ssh/known_hosts …`, mixed separators, printed space-separated and
  unquoted. A profile folder with a space (`C:\Users\Ana Maria`) split into several files; the parser now joins a word
  that does not start a path to the file before it.
- The system-wide config is `%ProgramData%\ssh\ssh_config`; the wrapper config includes it instead of
  `/etc/ssh/ssh_config`.

### The agent

- Windows ships the OpenSSH Authentication Agent service disabled. `ssh-add -l` then exits 2 with `Error connecting to
agent: No such file or directory`, as on macOS with no agent. With `SSH_AUTH_SOCK` unset, the app now reports
  `windows-agent-off`, whose remedy says an administrator turns the service on (P-89).

### The test hosts

- `docker compose` runs every test host on Docker Desktop's WSL 2 engine, the privileged systemd hosts included, with
  their ports on `127.0.0.1` only.
- Windows OpenSSH refuses a private key that other users can read (`UNPROTECTED PRIVATE KEY FILE`). The repository's
  drive grants Authenticated Users modify access, so `up.ts` gives `.run` an ACL that only the user holds, inherited by
  the keys.
- The daemon's musl tests run in the Ubuntu, Alpine and Rocky containers from Windows (`pnpm test:daemon`); cargo bakes
  the Windows path of `trcd` into them, so the containers get theirs through `TRC_TEST_TRCD`. One timing check (a
  command of `sleep 0.3` lasting at least 250 ms) failed once on Rocky under the parallel tests, the start mark read 60
  ms late in the busy VM; it now sleeps 0.5 s.

## UI Automation

`pnpm test:ax:win` reads the live terminal on `trc-ubuntu` through `tools/uia-probe`, in Electron 45's Chromium with
accessibility on, as Narrator turns it on (`terminal-windows.ax.test.ts`, 5 tests, and the probe's own 2, passing):

- **The element.** The focused text surface is an edit control (control type 50004, "edit") named with the session and
  host, holding keyboard focus, with a text pattern whose document is the screen's rows joined by line breaks.
- **No `TextPattern2`.** Chromium gives the surface `TextPattern` only, so there is no `GetCaretRange`. The caret is
  the collapsed selection range, which reports a 1-pixel rectangle at the terminal cursor; the test finds it within
  half a cell of the cursor cell. That is the caret UI Automation clients use without `TextPattern2`; whether
  Magnifier follows it as you type is `E6-manual-at.md` pass 9.
- **Read aloud from the pointer.** `RangeFromPoint` at a cell, expanded to its line, returns that row's text, as
  Magnifier's Ctrl+Alt+click starts from it (A11Y-06.5).
- **Selection.** A word chosen with the mouse is the text pattern's selection, with its text and bounds (A11Y-04.1).
- **Review mode.** The review field is an edit control too, holding the scrollback as its text, with its caret as a
  collapsed selection, and `RangeFromPoint` returns the line under the pointer there as well (A11Y-03).
- **The foreground lock.** An app started from a console in the background can't take the foreground, so the test's
  window stayed behind the owner's browser, which kept focus, and every read missed. `uia-probe foreground <pid>`
  attaches to the foreground window's input thread to hand the foreground over; only the test tooling does this, and
  the app never takes focus by itself.

Not covered here, and left to the manual passes before 1.0.0 (P-88): Narrator on the live terminal (pass 3), AltGr on
German and Brazilian layouts and the IME's candidate window (pass 12), Windows' text size (pass 10). Accessibility
Insights was not needed: the probe reads the same properties.

## Windows conventions found on the way

- **Context menus.** Windows sends its own `contextmenu` event, with no button (`button` -1), when the Menu key is
  released, after the key press that already opened the menu, so the terminal opened two in a row; Shift+F10 and a
  right-click opened one. The repeat is now dropped; a `contextmenu` with no key press before it, such as UI
  Automation's ShowContextMenu sends, is kept (`menu-key-echo.ts`, an e2e spec counts the menus).
- **Word selection.** Chromium on Windows selects the space after a double-clicked word, as Windows' text fields do;
  the terminal now drops it, as Windows Terminal and macOS do.
- **Playwright on Windows** starts Electron through `cmd.exe /d /s /c`, so `app.process()` is the shell: killing it
  leaves the app running, and the app's listeners belong to its child. Outside Playwright, the app's children exit
  within a second of a killed main process.

## Display preferences

- **Contrast themes.** With forced colors active, Chromium resolves the CSS system colors to the theme's and recolors
  the UI, as TECH_STACK §4.4 expects, but it also forced the text surface's transparent text to the theme's text color,
  painting every row over the canvas. The surface now opts out (`forced-color-adjust: none`, an e2e spec checks it
  under emulated forced colors), and with Match System the terminal takes its palette from the system colors (P-104).
  `nativeTheme.inForcedColorsMode` and `shouldUseHighContrastColors` reach the renderer through the display relay.
- **Animation effects** reach the app as Electron's `prefersReducedMotion`, which the relay already passes on.
- **Text size**, Windows' own setting, is left to the manual pass (`E6-manual-at.md`, pass 10): changing it changes
  the owner's whole session.
